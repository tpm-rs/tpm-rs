# Cryptographic Algorithm Audit: `tpm2-crypto-bssl` vs `bssl-crypto` / `bssl.rs` vs BoringSSL C

## 1. Executive Summary

This document audits the cryptographic implementations in [`crates/tpm2-crypto/bssl`](.), comparing:
1. **BoringSSL C Library (`bssl` / `bssl-sys`)**: The underlying C library and its raw FFI bindings.
2. **`bssl-crypto` & `bssl.rs` (Safe Rust Wrappers)**: Google safe Rust wrapper crate (`rust/bssl-crypto`) and local safe FFI bindings over `bssl-sys` (`src/bssl.rs`).
3. **`tpm2-crypto-bssl` (Current Crate)**: The TPM 2.0 cryptography backend in this repository (`BsslCryptoProvider`, implementing `tpm2::crypto::Crypto` and the static `tpm2::crypto::backend` family traits; unsupported algorithms are bound to `!`).

### Key Takeaways
- **BoringSSL C supports almost all required TPM 2.0 primitives natively**, including native AES-CFB-128 (`AES_cfb128_encrypt`), AES-192, CMAC (`<openssl/cmac.h>`), HMAC-SHA1, NIST P-256/P-384/P-521 (`EC_group_p256()`, `EC_group_p384()`, `EC_group_p521()`), pre-hashed IEEE P1363 ECDSA signing/verifying (`ECDSA_sign_p1363` / `ECDSA_verify_p1363`), arbitrary EC point multiplication (`EC_POINT_mul`), and full RSA padding/encryption/signing/modpow operations.
- **`bssl-crypto` (the safe Rust wrapper) is very opinionated and intentionally restricted**: It omits CMAC, HMAC-SHA1, AES-192, AES-CFB, P-521, arbitrary EC point multiplication, RSA encryption/decryption, and only provides high-level message signing (hashing the message internally rather than accepting pre-hashed digests).
- **Safe FFI bindings in `src/bssl.rs`**: To use BoringSSL C primitives where `bssl-crypto` lacks APIs, `tpm2-crypto-bssl` enforces `#![deny(unsafe_code)]` at the crate root and `#![forbid(unsafe_code)]` on all modules except `src/bssl.rs`, which encapsulates safe RAII wrappers over `bssl-sys` for HMAC (`Hmac<N>`), AES-128/192/256-CMAC, the AES modes (`Aes`), RSA keys (`RsaPublic`, `RsaPrivate`: RSASSA, RSAPSS, RSAES, RSA-OAEP, RSA-NULL, key generation and import), NIST P-224/P-256/P-384/P-521 + BN-P256 curve operations and ECDSA, and ML-KEM-768/1024 / ML-DSA-44/65/87.
- **ML-KEM and ML-DSA**: BoringSSL implements ML-KEM-768/1024 and ML-DSA-44/65/87 key generation, pure ML-DSA `mu` and verification (`src/bssl.rs`); ML-KEM-512, ML-DSA signing with a caller-supplied `rnd` and HashML-DSA fall back to the RustCrypto keys of `tpm2-crypto-rust` (through its `tpm2::crypto::backend` implementation), as BoringSSL lacks them.
- **Completed Migrations**: SHA-1, SHA-256/384/512, HMAC, AES-128/192/256-CMAC, the AES modes, RSASSA, RSAPSS, RSAES, RSA-OAEP, RSA-NULL, RSA Keygen, RSA Import/Export, NIST P-224/P-256/P-384/P-521, and BN-P256 all use BoringSSL (`bssl-crypto` or `bssl-sys` via `src/bssl.rs`), with no RustCrypto `sha1`, `sha2`, `hmac`, `cmac`, `aes`, `camellia`, `digest`, `p256`, `p384`, `p521`, `rsa`, or `rand` dependencies in `Cargo.toml` (Camellia comes through `tpm2-crypto-rust`). Only `rand_chacha` (`ChaCha20Rng`) is used, for the deterministic RNG of `Random::from_seed` (BoringSSL lacks a deterministic seeded PRNG API).

## 3. Detailed Component Analysis

### 3.1 Random Number Generation (`src/lib.rs`)
- **Current State**: `tpm2::crypto::Random` is implemented on `BsslCryptoProvider` with `type Rng = BsslRng`: `from_entropy` is BoringSSL's `RAND_bytes` (`bssl_crypto::rand_bytes`; `stir_bytes` does nothing, as BoringSSL reseeds `RAND_bytes` itself and takes no additional input), `from_seed` a `rand_chacha::ChaCha20Rng` seeded with SHA-256 of the seed (`stir_bytes` reseeds it with SHA-256 of 32 output bytes and the data, deterministically), and `rand_bytes` calls `RAND_bytes` directly. `BsslRng` also implements `rand_core::RngCore`, the randomness source of RSA and ECC key generation. `Crypto::ct_eq` uses `bssl_crypto::constant_time_compare` (`CRYPTO_memcmp`).
- **C BoringSSL vs `bssl-crypto`**:
  - BoringSSL C provides `RAND_bytes` in `<openssl/rand.h>`.
  - `bssl-crypto` safely exposes this as `bssl_crypto::rand_bytes`.
  - Used directly with zero RustCrypto fallback.

### 3.2 Hash & HMAC (`src/hash.rs`, `src/bssl.rs`)
- **Current State**:
  - `BsslSha1`, `BsslSha256`, `BsslSha384`, `BsslSha512` use `bssl_crypto::digest` (`InsecureSha1`, `Sha256`, `Sha384`, `Sha512`).
  - `BsslHmac<N>` (`BsslHmacSha1`/`256`/`384`/`512`) uses `crate::bssl::Hmac<N>`, a safe wrapper in `src/bssl.rs` over `bssl_sys::HMAC_CTX` with the `EVP_sha*()` of the `N`-byte digest.
  - Unsupported hash algorithms (SM3-256, SHA3-256, SHA3-384, SHA3-512) are bound to `!`.

### 3.3 CMAC (`src/cmac.rs`, `src/bssl.rs`)
- **Current State**: Uses safe wrappers `crate::bssl::{CmacAes128, CmacAes192, CmacAes256}` over BoringSSL's `bssl_sys::CMAC_CTX` (`<openssl/cmac.h>`) with `EVP_aes_128_cbc()`, `EVP_aes_192_cbc()`, and `EVP_aes_256_cbc()`. SM4 is bound to `!`. BoringSSL is built without Camellia (`OPENSSL_NO_CAMELLIA`), so Camellia-128/192/256 are the CMAC states of `tpm2-crypto-rust` (RustCrypto `cmac` and `camellia`).

### 3.4 Symmetric Ciphers & Block Cipher Modes (`src/symmetric.rs`, `src/bssl.rs`)
- **Current State**:
  - `BsslAes<KEY>` wraps `crate::bssl::Aes` (both AES key schedules, `AES_set_encrypt_key`/`AES_set_decrypt_key`) and implements `SymmetricState`: CTR (`AES_ctr128_encrypt`), OFB (`AES_ofb128_encrypt`), CBC (`AES_cbc_encrypt`), CFB (`AES_cfb128_encrypt`, full-block feedback) and ECB (`AES_encrypt`/`AES_decrypt`), each updating the IV in place with the chaining value of the TCG reference. After a partial final CFB block, BoringSSL leaves the partial ciphertext followed by keystream in the IV; the default `SymmetricState::crypt` zero pads it to the TPM's chaining value.
  - Camellia-128/192/256 in every mode are the cipher states of `tpm2-crypto-rust` (RustCrypto `camellia`), since BoringSSL is built without Camellia.
  - SM4 is bound to `!`.

### 3.5 Asymmetric RSA (`src/rsa.rs`, `src/bssl.rs`)
- **Current State**: `BsslRsa<MOD, PRIME>` (RSA-1024/2048/3072/4096) holds a `crate::bssl::RsaPrivate` (a BoringSSL `RSA` with all CRT components) and its `BsslRsaPublicKey` (`crate::bssl::RsaPublic`: `RSA_new_public_key`, which checks the key). The `rng` arguments of the operations are unused (BoringSSL blinds and pads with its own RNG).
  - **RSASSA (PKCS#1 v1.5)**: `RSA_sign` and `RSA_verify`.
  - **RSAPSS**: `RSA_sign_pss_mgf1` with the largest salt up to the digest size (TPM 2.0 `PssEncode`; e.g. 62 bytes for SHA-512 with RSA-1024) and `RSA_verify_pss_mgf1` with `RSA_PSS_SALTLEN_AUTO` (any salt, TPM 2.0 `PssDecode`).
  - **RSAES (PKCS#1 v1.5)**: `RSA_encrypt` and `RSA_decrypt` with `RSA_PKCS1_PADDING`.
  - **RSA-OAEP**: `EVP_PKEY_encrypt` / `EVP_PKEY_decrypt` with `RSA_PKCS1_OAEP_PADDING`, OAEP MD, MGF1 MD, and label ownership via `EVP_PKEY_CTX_set0_rsa_oaep_label` (the label includes the TPM label's terminating zero).
  - **RSA-NULL**: `RSA_encrypt` / `RSA_decrypt` with `RSA_NO_PADDING` after validating $m < n$ (or $c < n$) via `BIGNUM`.
  - **RSA Import / Export**: `RsaPrivate::from_prime` (`PrivateKey::load`, with either prime: computes $q = n/p$, checks primality of $p$ and $q$ via `BN_primality_test`, derives $d = e^{-1} \bmod \lambda(n)$ and the CRT parameters via `BN_*` arithmetic, and constructs `RSA_new_private_key`), `RsaPrivate::prime` (`PrivateKey::store`, `RSA_get0_p`) and `RsaPrivate::crt` (`RsaKey::store_crt`, `[p, q, dP, dQ, qInv]` with the larger prime first).
  - **RSA Key Generation** (`PrivateKey::generate`), for any odd exponent >= 3:
    - **RNG of `from_entropy`**: BoringSSL's `RSA_generate_key_ex` for 1024, 2048, 3072, and 4096-bit keys.
    - **RNG of `from_seed`** (deterministic): the prime candidates come from the seeded ChaCha20 RNG, and `bssl-sys` (`Bignum`, `BN_gcd`, `BN_primality_test`, `RSA_new_private_key`) generates primes $p$ and $q$ with $\gcd(p - 1, e) = 1$ and computes the CRT parameters.

### 3.6 ECC Curves: NIST P-224, P-256, P-384, P-521, BN-P256 (`src/ecc.rs`, `src/bssl.rs`)
- **Current State**: `BsslEcc<G, COORD, POINT>` (the private scalar, cleansed on drop, and its validated public point `BsslEccPublicKey`) implements `EccCurve` for the curve `G` (`NistP224Group`, ..., `BnP256Group`, each selecting an `EcGroup`): `load_public` validates the point, `load` checks `[d]G` against the public key, `ecdh` is `[d]Q` (all these curves have cofactor 1), and `mul_generator`/`mul_point` are the tpm-rs point multiplications. SM2 signatures are not supported (the trait defaults); the ECDSA nonce comes from BoringSSL's RNG.
  - **NIST P-224, P-256, P-384, P-521**: All operations (point validation `ec_validate_point`, generator multiplication `ec_point_multiply_generator`, arbitrary point multiplication `ec_point_multiply`, pre-hashed IEEE P1363 ECDSA signing/verification `ecdsa_sign`/`ecdsa_verify`, and deterministic/random key generation `ec_generate_key`) are implemented in `src/bssl.rs` using BoringSSL's `EC_group_p224()`, `EC_group_p256()`, `EC_group_p384()`, `EC_group_p521()`, `EC_POINT_mul`, `EC_POINT_get_affine_coordinates_GFp`, `ECDSA_sign_p1363`, and `ECDSA_verify_p1363`.
  - **BN-P256**: Implemented 100% via BoringSSL's custom curve APIs (`EC_GROUP_new_curve_GFp` and `EC_GROUP_set_generator`) backed by `EC_GFp_mont_method()` in `src/bssl.rs` (`EcGroup::BnP256` with scoped RAII `EcGroupHandle`). Supports point validation, generator multiplication, arbitrary point multiplication, ECDSA signing/verification, and key generation.

### 3.6a ECC Curves: NIST P-192, BN P-638, SM2 P-256 (`src/ecc.rs`)
- **Current State**: The key types are the shared generic implementation of the `tpm2-crypto-weierstrass` crate (`tpm2_crypto_weierstrass::{NistP192, BnP638, Sm2P256}`, also used by the Rust and Crux backends): Montgomery arithmetic with runtime moduli (`crypto-bigint` `DynResidue`), a Montgomery ladder with constant-time swaps over the complete projective addition formulas of Renes-Costello-Batina 2016 (algorithm 1, general `a`; all three curves have cofactor 1), and curve parameters from `tpm2::crypto::ecc_params`. Key generation draws the private scalar by rejection sampling from the `BsslRng` (seeded ChaCha20 / BoringSSL RNG), as for the other curves. The crate also implements SM2 signatures on these curves. No ECDAA (computed by `tpm2-engine`).
- **Why not BoringSSL**: BN P-638 does not fit BoringSSL's `EC_MAX_BYTES` (66). NIST P-192 and SM2 P-256 could be custom `EC_GROUP_new_curve_GFp` groups like BN-P256, but the generic crate avoids more unsafe FFI and keeps one implementation of these curves across the backends.

### 3.7 ML-KEM and ML-DSA (`src/pqc.rs`, `src/bssl.rs`)
- **Current State**: Private keys are seeds (ML-KEM `d || z`, ML-DSA `xi`, cleansed on drop) with their encoded public keys. The derandomized operations (`MlkemKey::encapsulate_internal`, `MldsaKey::sign_mu_internal`) take the TPM's `m` and `rnd`; the randomized ones (`generate`, `encapsulate`, `sign_mu`, `sign_message`) draw them from the `BsslRng`.
  - **ML-KEM-768/1024**: `src/bssl.rs` (`mlkem768`, `mlkem1024`) expands the seed (`MLKEM*_private_key_from_seed`) and marshals the public key; encapsulation parses the key with `EVP_PKEY_from_raw_public_key` (BoringSSL's parser performs the modulus check of FIPS 203, Section 7.2, so an invalid key is `InvalidData`) and encapsulates with `EVP_KEM_encap_external_entropy_for_testing`; decapsulation is `MLKEM*_decap`. Private key structures are cleansed on drop (`CleansedKey`).
  - **ML-DSA-44/65/87**: key generation (`MLDSA*_private_key_from_seed`, `MLDSA*_public_from_private`, marshalled into a fixed `CBB`), the `mu` of pure ML-DSA with a context string (`MLDSA*_prehash_init`/`_update`/`_finalize`), public key validation and verification on `mu` (`MLDSA*_parse_public_key`, `MLDSA*_verify_message_representative`) use BoringSSL.
  - **Fallbacks**: ML-KEM-512 (not in BoringSSL; `BsslMlkem512` wraps the key of `tpm2-crypto-rust`), ML-DSA signing (no public API with a caller-supplied `rnd`; the `tpm2-crypto-rust` key is expanded from the seed to sign `mu`) and HashML-DSA (not in BoringSSL) use RustCrypto `ml-kem`/`ml-dsa` through the `tpm2::crypto::backend` implementation of `tpm2-crypto-rust`.

### 3.8 Error Mapping (`src/bssl.rs`, `src/lib.rs`)
- **Current State**: The safe bindings in `src/bssl.rs` return `BsslError` (`Unsupported`, `InvalidData`, `BufferTooSmall`, `Internal`). The `tpm2::crypto::backend` trait implementations map them to the `tpm2::crypto` conventions:
  - `InvalidData` (a bad key, signature, point, scalar, ciphertext, padding or label, or a message too large for the key) is a semantic failure reported in the `Ok` value: `Ok(false)` for verification and point validation, `Ok(None)` for encryption, decryption, key and point loading, ECDH and point multiplication.
  - `Unsupported` becomes `CryptoError::Unsupported`; `BufferTooSmall` and `Internal` (and `InvalidData` for operations without semantic failures, such as key generation) become `CryptoError::Internal`.
  - RSAES/OAEP encryption (`RSA_encrypt`, `EVP_PKEY_encrypt`) and RSAES/OAEP decryption (`RSA_decrypt`, `EVP_PKEY_decrypt`) failures are input-caused (message too large, bad padding or label), so they are reported as `InvalidData`. Signing has no semantic failures in the backend traits (the dispatch code checks the sizes), so a failure of `RSA_sign`/`RSA_sign_pss_mgf1`/`ECDSA_sign_p1363` is `CryptoError::Internal`.
